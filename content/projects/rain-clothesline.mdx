## Overview

Open-air drying is a race against the weather. Laundry left out during a sudden downpour comes back wetter than it went out, and nothing about a manual clothesline notices the first drops.

This build turns the clothesline into a small closed-loop machine: a nickel-plated serpentine sensor board (conditioned by an LM393 comparator) reports rain, and an SG-90 servo swings an arm that retracts the line under cover. When the plate dries, the arm extends again.

Key focus areas:
- Detecting the first drops without false triggers from dew or mist
- Two-state actuation with a hard, repeatable arm position at each end
- Continuous serial visibility into what the sensor is reporting
- One firmware image that tolerates multiple Uno board revisions

The comparator's polarity is what makes the logic so short: moisture is a **LOW**, so the retract branch is the safety-default and a disconnected or failed jumper reads as dry rather than falsely raining.

### Firmware

```cpp
#include <Servo.h> // servo library
Servo s1;
int val = 0;

void setup()
{
    Serial.begin(9600);
    pinMode(7, INPUT);  // Rain sensor output pin connected
    s1.attach(6);       // Servo Motor
}

void loop()
{
    val = digitalRead(7);   // Rain sensor output pin connected
    Serial.println(val);    // see the value in serial monitor
    delay(100);

    if (val == 0)
    {
        s1.write(90);   // Servo Rotate 90 Degree
        delay(500);     // delay time
    }

    if (val == 1)
    {
        s1.write(0);    // Servo Rotate 0 Degree
    }
}
```

## Technical Challenges

<ChallengeCard
  title="False Positives From Dew and Mist"
  problem="Morning condensation and light mist were enough to read as rain and retract the line on a clear morning."
  solution="Tuned the LM393's onboard potentiometer so the comparator only trips once droplets actually bridge adjacent traces, keeping the trigger threshold in hardware where it belongs."
  result="Dew and humidity no longer trigger a retraction, while the first real drops still flip the state on the next 100 ms poll."
/>

<ChallengeCard
  title="Flashing Firmware Across Two USB Stacks"
  problem="Uploads failed intermittently depending on which Uno was connected — the board's native ATmega16U2 CDC-ACM path and a third-party WCH CH340G USB-UART bridge enumerate differently."
  solution="Diagnosed the driver mismatch with device-manager and lsusb inspection, installed the CH340/CH341 driver alongside the native CDC-ACM stack, and verified the correct COM/tty device before every upload."
  result="A repeatable flash workflow across boards and operating systems, no more guessing why a compile succeeded but the upload did not."
/>

<ChallengeCard
  title="Deadband Between the Two States"
  problem="A two-state arm needs hard endpoints — a partially retracted line is the worst outcome in a downpour."
  solution="Mapped the arm to absolute angles (0° deployed, 90° retracted) instead of incremental steps, so every command drives the servo to a known position from any previous state."
  result="Predictable covered or uncovered states with no drift, and recovery is just a power cycle back to a defined angle."
/>

## Lessons Learned

*   **Put thresholds in hardware when you can:** one trimpot replaced a pile of software filtering for mist and dew.
*   **Absolute positions beat increments:** angle-based commands make a two-state mechanism self-recovering.
*   **Instrument everything:** printing the raw sensor value each loop turned a vague "it didn't trigger" into an obvious wiring or polarity problem.
*   **Drivers are part of the stack:** knowing which USB-UART bridge a board uses saves hours of "why won't it upload" debugging.
*   **Next iteration:** add a debounce window and a hold-off timer so a single stray drop does not cause a retract-and-redeploy cycle.
